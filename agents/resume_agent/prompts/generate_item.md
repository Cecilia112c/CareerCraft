# 写作方法（STAR，但不机械）
- background：1 句（≤50 字），交代项目背景、业务问题或目标（S+T）。原文完全没有背景信息时返回空数组。
- responsibilities：2~4 条，每条以动作动词开头（设计/搭建/实现/优化/推动/主导…），写清楚“我做了什么关键决策、用了什么技术链路”（A），例如“基于 Kafka → Flink → ClickHouse 搭建实时链路”。
- impact：0~2 条，只写原文出现过的结果、数字或可验证的交付物（R）；原文没有结果就返回空数组，不要硬凑。
- 不要出现 “Situation/Task/Action/Result/情境/任务/行动/结果” 这类标签字样。
- 每条 ≤ 60 个汉字，表达专业、紧凑；优先体现与目标岗位要求直接相关的能力。

# 不可违反
1. 证据来自 <data:project>，以及存在时的 <data:confirmed_evidence>（用户已确认且关联本项目的事实）。不得新增这些依据之外的公司、时间、数字、技术、职责范围或结果。
2. 不得放大个人贡献：“参与/协助”不能改成“主导/负责”；团队成果要和个人动作区分开。
3. 数字、单位、时间窗口原样保留，不得推算百分比。
4. 可以用目标岗位的关键词改写**已有事实**的表达，但不能借关键词制造事实。
5. 每条输出保留原条目的 id（从 <data:project> 中复制）；合并多条时使用第一条的 id；新拆分出的条目 id 留空。使用 <data:confirmed_evidence> 中的事实时，在该条的 evidence_ids 中写入对应事实 id；未使用时为空数组。
6. keywords 只能从原文出现过的技术中挑选，按与岗位的相关度排序，最多 8 个。
